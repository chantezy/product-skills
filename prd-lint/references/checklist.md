# PRD 逻辑评审检查清单

每个检查项包含：**检查什么** → **怎么判定** → **高频漏法**。

A / B / C 三个维度必查。D 维度为附加项。

---

## A. 可追溯性（必查）

核心问题是「功能方案是否真的对应需求背景里提出的问题」。必须**双向查**。

### A1 正向映射：问题 → 功能

- **检查**：问题清单（P\*）中的每一条，是否存在至少一个功能点（F\*）或规则（R\*）明确承接它
- **判定**：找不到承接，按该问题是否为文档自述的核心目标，标「阻塞」或「高风险」
- **高频漏法**：背景写了 3 个痛点，功能只覆盖 2 个；最后一句话带过的痛点没进功能清单

### A2 反向反查：功能 → 问题

- **检查**：功能清单（F\*）中的每一项，能否回答「它解决哪个 P\*」
- **判定**：答不上来的功能，标「高风险」，问题描述为「无来源需求」
- **高频漏法**：功能列表里突然出现的「顺便做一下」的能力

### A3 目标与指标对应

- **检查**：目标（G\*）是否对应到某个 P\*，且可量化、可判定
- **判定**：不可量化的目标（如「提升使用体验」）标「建议」
- **高频漏法**：目标章节与背景章节各说各话，二者无引用关系

### A4 范围边界

- **检查**：是否声明了本期不做什么
- **判定**：没有范围声明时，仅在文档中出现了明显可能被误解为「已包含」的能力时才提示，不无条件要求补写

### A5 优先级依据

- **检查**：功能优先级是否来自目标或问题，而非只给 P0 / P1 标签而无理由
- **判定**：无依据的优先级标记为「建议」

---

## B. 逻辑完整性（必查）

核心问题是「流程、状态、分支有没有断点」。

### B1 流程闭环

- **检查**：主流程是否有明确起点、正常路径、结束态；是否存在只有入口没有出口的环节
- **判定**：断点标「阻塞」

### B2 状态覆盖

- **检查**：每个界面或环节是否覆盖：首次空态、加载中、请求失败、无权限、超限（数量 / 长度 / 频率 / 额度）
- **判定**：核心链路上的缺失标「高风险」，边缘状态标「建议」
- **高频漏法**：只写主流程，不写空态与失败态——这是出现频率最高的漏法

### B3 分支穷尽

- **检查**：条件判断（if / else）是否闭合；是否存在「其余情况不处理」
- **判定**：存在未覆盖分支且会影响结果时，标「高风险」

### B4 操作可逆性

- **检查**：删除、覆盖、退出等破坏性操作是否有二次确认或撤销；不可逆操作是否有说明
- **判定**：不可逆且无确认，标「高风险」

### B5 状态机穷尽

- **检查**：若文档描述的对象存在多个状态，列出全部状态 + 迁移条件 + 触发方；检查有无未定义迁移
- **判定**：未定义迁移会造成实现期歧义，标「阻塞」或「高风险」
- **方法**：先列状态集合，再列迁移矩阵，空格即为缺口

### B6 角色与权限

- **检查**：每个角色在每处入口的可见范围与可执行操作是否都定义；越权路径是否说明
- **判定**：缺失标「高风险」

### B7 入口与端

- **检查**：多端（Web / 移动 / 客户端）或多入口（列表页 / 搜索页 / 分享链接）是否都说明差异
- **判定**：只描述一端而实现需要多端覆盖时，标「高风险」

### B8 时序与并发

- **检查**：存在先后依赖的操作是否说明顺序约束；并发编辑、重复提交如何处理
- **判定**：缺失标「高风险」

### B9 数据流向

- **检查**：数据的来源、存储位置、消费方是否说明；展示值是否说明从何计算
- **判定**：缺失标「建议」，仅在影响正确性时升级

## C. 一致性（必查）

核心问题是「文档内部有没有互相打架」。冲突必须拆成下面几种分别查，否则会漏。

### C1 功能间结果一致

- **检查**：同一操作在不同功能、不同入口下的结果是否一致
- **判定**：不一致标「阻塞」——它意味着实现时必须二选一
- **方法**：找出所有会改变同一对象状态的入口，横向比对

### C2 术语统一

- **检查**：构建术语表——同一概念是否出现多个名称（一物多名）；同一名称是否有多种含义（一名多义）
- **判定**：标「高风险」，术语混乱会直接导致开发理解偏差
- **方法**：抽取文档中所有名词性关键词（功能名、字段名、对象名、状态名），两两比对

### C3 规则冲突与仲裁

- **检查**：规则清单（R\*）两两比对——是否存在条件重叠但结论不同的规则对；多条规则同时命中时谁优先是否明确
- **判定**：**冲突且无优先级说明 = 最严重的漏点，标「阻塞」**
- **说明**：这是出现频率最高的漏点，务必逐对检查，不要抽样

### C4 数值一致性

- **检查**：所有限制值（数量上限、字符长度、时效、超时、分页大小、默认值）在不同章节出现时是否一致
- **判定**：不一致标「高风险」
- **方法**：全文提取所有数字 + 单位 + 所在章节，分组比对

### C5 数据口径

- **检查**：单位、时区、精度、统计范围（是否含某类数据）、计算时点是否统一
- **判定**：不一致标「高风险」

### C6 文案与反馈一致

- **检查**：同一状态在不同模块的提示文案、状态色、交互反馈是否一致
- **判定**：标「建议」

### C7 背景与方案自洽

- **检查**：背景章节的描述与功能方案章节是否互相矛盾
- **判定**：标「高风险」或「阻塞」
- **示例**：背景写「用户不会使用复杂筛选」，方案却引入多层嵌套条件

## D. 落地质量（附加项）

> **缺失不报。** 仅当文档已经写了这类内容时，才检查其是否自洽。文档未写验收标准、埋点、依赖项、非功能需求，不产出任何条目。

### D1 验收标准可判定

- **检查**：已写出的验收标准是否可测、可判定（有明确的通过条件）
- **判定**：写了但不可判定，标「建议」

### D2 分期与优先级

- **检查**：已给出的 MVP / 后续划分是否与功能清单一致（有无功能既未进 MVP 也未进后续）
- **判定**：不一致标「高风险」

### D3 埋点与数据

- **检查**：已定义的埋点事件、属性是否覆盖文档自述的目标指标（G\*）；口径是否与 C5 一致
- **判定**：覆盖缺口标「建议」

### D4 依赖项

- **检查**：已列出的依赖（上游数据、其他团队、第三方能力）是否与功能描述匹配；有无功能依赖了未列出的能力
- **判定**：标「高风险」

### D5 非功能需求

- **检查**：已写出的性能、兼容性、安全要求是否与功能描述冲突
- **判定**：冲突标「高风险」

---

## E. 跨文档一致性（默认执行）

> 详细检索流程见 `references/cross-doc-search.md`。本节只列检查项。

核心问题是「新 PRD 的规则跟线上已有功能是否矛盾」。必须基于**最新版本**的线上文档判定，每条结论附依据文档的标题、更新时间与链接。

### E1 规则结论冲突

- **检查**：新 PRD 的规则与线上最新文档的规则结论是否相反
- **判定**：**结论不同且新 PRD 未说明这是变更，标「阻塞」**
- **说明**：新 PRD 主动声明「变更 / 升级 / 替代」线上规则的不算冲突，按 A 维度正常覆盖处理

### E2 同一操作结果不一致

- **检查**：同一操作在线上文档与新 PRD 中的结果（跳转去向、状态变化、提示文案）是否一致
- **判定**：不一致标「阻塞」

### E3 规则沿用未说明

- **检查**：线上已有规则，新 PRD 涉及同一模块但未说明是沿用还是修改
- **判定**：标「高风险」——开发无法判断是否要保留原逻辑

### E4 命名与字段不一致

- **检查**：新 PRD 使用的字段名、功能名与线上文档是否一致
- **判定**：标「高风险」——容易导致开发理解为两个不同对象

### E5 限制值不一致

- **检查**：数量上限、字符长度、时效、默认值等与线上文档是否一致
- **判定**：不一致且未说明，标「高风险」

### E6 引用的线上规则已变更

- **检查**：新 PRD 引用或依赖的线上规则，其最新版本是否已经发生变化
- **判定**：标「高风险」——引用过期规则会导致实现与现网不符

### E7 线上文档自身存在多版本矛盾

- **检查**：同一功能的线上文档内部描述前后矛盾；或同功能多份文档结论不同
- **判定**：标「高风险」，在报告中列出全部候选文档供用户判断

---

## 无法判断的情形

以下情形归入「待确认」分区，**不判定为错误**：

- 文档引用但未展开的外部规范、设计稿、接口文档
- 一句话概述但明显由独立文档承载的模块
- 表述存在多种合理解读，且无法从上下文排除
